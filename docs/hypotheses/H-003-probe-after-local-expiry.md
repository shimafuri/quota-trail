## 仮説

`.credentials.json` の `claudeAiOauth.expiresAt` を過ぎた access token でも、`/api/oauth/usage` がしばらく 200 を返す場合がある。§15 のローカル期限 gate（`auth_expired_local`）はこの区間も一律に「認証更新待ち」にしており、本来取れたはずのサンプルを欠測にしている可能性がある。期限切れ token ごとに 1 回（またはごく少数回）だけ確認の送信をすれば、401→429 の連鎖を再発させずに、受け付けられるかどうかを実測しながら欠測を減らせる。

## 現状の診断

- 運用ログ（`%APPDATA%/quota-trail/logs/quota-trail.log{,.1}`）の Claude の tick 結果を日別に数えた結果:
  - 9/20–9/22、9/25–9/28: アプリはほぼ 24 時間稼働（1 日約 478 tick）。期限切れでも送信する旧コード（HEAD の `providers/claude.mjs`）で、401 は 9/24 の 3 回だけ
  - 9/30、10/1: `auth_expired` 24 回 / 21 回、`http_429` 150 回 / 146 回（§15.2 の「401 → 429 約 1 時間」の反復）
  - 10/2 以降（ローカル gate 導入後）: `auth_expired_local` が 1 日 28〜318 tick。10/10 は約 16 時間分
- 10/2 以降のログでは、新 token 検知から次の `expiresAt` まで毎回約 28,790 秒（8 時間）。token 寿命は観測期間中変わっていない
- 9/20–9/28 に Claude Code を 8 時間以上使わなかった時間帯があったかは、`~/.claude/projects` の transcript の時刻だけでは判定できなかった（transcript に記録されない利用・更新経路があり、10/5 には transcript 上の無活動が 8 時間を超えていても、ローカル gate 下で取得に成功している）。そのため「9 月は期限切れ token が受け付けられていた」とは確証できない
- 401 後の 429 連鎖は、同じ失効 token を 3 分ごとに再送したことが引き金だった可能性がある。§15.4 の「401 を受けた token は再送しない」規則はその反復経路を止めるが、1 回の要求でも 429 が生じないとは保証しない。ローカル gate がそれに追加で何を防いでいるかは未実測

## 採用したときの形

1. ローカル期限切れの token について、3m/30m/2h/6h/8h の一段を順に割り当て、usage への確認送信を最大 1 回許可する。各段の許容遅れは 0〜300 秒。401 を受けたら §15.4 の `cached_401` で以後の送信を止める
2. 確認送信の結果（200 / 401 / 429、段、実際の期限後経過秒、skip 理由）を専用ログイベントに記録し、複数 token の段別の受付状況を実測する
3. 200 が返ったサンプルは通常の値として記録する（error 行にしない）。表示上は期限超過中であることを区別できるようにするかを設計で決める
4. 設定 off、期間・予算上限、429 により確認送信を止めて現行の gate に戻せるようにする。全段で受付を観測しなくても、期限後の受付が一切ないという証明にはしない

## 反証条件・コスト・リスク

- 確認送信がすべて 401 を返すなら、観測範囲で期限後の受付を得られなかったとして継続の価値を見直す。**2026-10-11 評価で改訂**: 全 401 だけから「期限後の受付が一切ない」や「原因は Claude Code を使わない時間 > 8h」とは判断しない。利用不在の証拠と、過去の期限後受付との比較は別に必要（design.md §15.12）
- 1 回の確認送信でも 429 の連鎖やアカウント側の制限を招くなら棄却
- 期限切れ token の送信は §15.1 の方針（期限切れ要求をなくす）に部分的に逆行する。送信回数の上限と 401/429 時の停止規則が必須

## 評価後の到達範囲（2026-10-11）

採用先は [design.md §15.12](../design.md#1512-期限超過後の確認送信2026-10-11-追加)。**2026-10-11 レビュー反映**で、600 秒固定窓を **3m → 30m → 2h → 6h → 8h** の token ごとの順次割当に変更した。各段の送信開始窓は予定から 0〜300 秒、最長 8h5m。満杯の段を飛ばし、未送信失効でもカーソルを進め、同 token を別段へ再配布しない。複数 token から数分・数十分・数時間の受付曲線を得るが、一つの token の連続受付や十数時間の欠測全体を説明する測定ではない。

比較対照は期限直前の最後の通常 usage 成功（180 秒 tick なら期限前余裕 30 秒超〜390 秒）。鮮度を期限に対して評価して保持するため、8h 待っても対照自体を古さで失格にしない。対照から送信まで token・dir・expiresAt・要求条件を再確認する。新 token が来たら旧未使用予算は失効させ、A→B→A、設定 OFF→ON、cache 除去でも復活させない。起動時/ON 時から expired、対照なし、窓超過、既知 401、期限改変・要求条件変更・資格情報読取失敗・時計不適格には送らない。

時計判定には睡眠/休止を含む OS 経過時計を注入し、壁時計との累積差 60 秒以上・後退を検出する。suspend/resume を記録し、JS 単調時計が睡眠中に止まるだけでは clockSuspect にしない。resume でも基準をリセットせず補正を検査し、窓内なら送信可、窓超過は失効。睡眠を含む時計が使えなければ clock_unverified として送信しない。

usage は送信前に予算を消費して最大 1 回、profile は 0。network/timeout も再試行しない。**6h/8h の 200 でも通常取得を再開しない**。一点の成功では次回受付を保証できず、実測の条件と安全上限を守るため、ローカル health は expired のままとする。正常点は既存 DB 列に保存し、probe の由来は専用ログで区別する。帰属は同 token の権威 profile cache のみ、なければ unknown。実際の probe 429 は既存のアプリ共通の次回 2 倍に反映し、次の要求を許す前に実測を中止して設定 off へ戻す。

期間は最初の once 有効化から最大 7 日（途中 OFF・睡眠も含む）、予算は各段 4・合計 20 token の送信前消費とし、早い方で自動停止する。未送信 skip は送信枠を消費せず、送信失敗・未完了は安全予算に含む。OFF→ON で期間/予算をリセットせず、閉じたセッションは同プロセスでは再開しない。128 件非削除台帳は失効履歴/401 禁止の復活を防ぐため維持する。再起動は別セッションで、既に expired の token には再配布せず、異なる 20 token の集計には合算しない。

受付は段別の 200/401 と実際の超過秒で評価し、HTTP 200 と有用サンプル数を分ける。status 未確認の失敗・429・skip・未完了は受付分母に含めず、未観測を 0% にしない。全段各 4 件が全 401 なら今回の各窓で受付を観測しなかったとして off を維持し、一段でも不足ならその段は件数不足。短時間段の全拒否で夜間数時間の問いに回答せず、token 更新による長時間段の脱落も示す。6h/8h の 200 はその実時間の受付を示すが、それ以前の連続受付や全 token の猶予は証明しない。

受付なしの恒久自動判定は設けない。段別の判断表・過去と同じ経過時間帯での比較に必要な証拠・実装時のテストと受け入れ条件は採用先を正とする。本評価は設計判断であり、期限後の 200 を実測したことや、Anthropic の仕様変更・Claude Code 不在を確定したことを意味しない。
