# 設計仮説（Design Hypotheses）

要件（発注者の指示・`docs/requirements*.md`）と設計書（`docs/design*.md`）の間に置く、**「設計の改善に繋がる仮説」の置き場**である。

## 何を置くか

- まだどの設計書にも採用されていないが、次に設計・最適化をするときに参照すべき仮説
- 外部の論文・製品・会話から得た着眼で、quota-trail の構造に翻訳し直したもの
- 「今の構造のどこが、なぜ限界か」の診断と、それを解く方向の候補

**置かないもの**: 既に採用済みの設計判断（それは設計書の本文にある）、バグ・残課題（issue / 設計書の実装ノート）、要件そのもの。

## いつ参照するか

1. **設計書を書くとき** — 設計依頼プロンプトに、対象領域に関係する仮説ファイルのパスを必ず含める。設計者は各仮説について「採用 / 部分採用 / 却下 / 対象外」を設計書に明記する
2. **実装を最適化するとき** — 設計書を読むのと同時に、その設計が採用しなかった仮説を読み、最適化が仮説の方向と逆行していないかを確認する
3. **要件を書くとき** — 仮説が要件に昇格すべきかを判断する

## ライフサイクル

| status | 意味 |
|---|---|
| `proposed` | 置いただけ。まだどの設計にも当てられていない |
| `evaluated` | ある設計書で検討され、採用 / 部分採用 / 却下の判断が付いた（判断と設計書名を `decisions` に追記） |
| `adopted` | 設計書に取り込まれ、仮説としての役目を終えた（ファイルは残し、採用先を指す） |
| `refuted` | 実測や実装で反証された（反証の根拠を残す） |

判断が付いても**ファイルを消さない**。却下された理由は、次に同じ発想が出たときの最短の答えになる。

## ファイル形式

`H-NNN-<slug>.md`。frontmatter に `id` / `title` / `status` / `origin`（出典）/ `areas`（関係する設計書）/ `decisions`（設計書ごとの判断）。本文は次の 4 節を持つ。

1. **仮説** — 1〜3 文。反証可能な形で書く
2. **現状の診断** — quota-trail のどの構造が、なぜこの仮説の対象になるか（ファイル名・数値を挙げる）
3. **採用したときの形** — 設計へ落とすときの具体像。段階があれば順序
4. **反証条件・コスト・リスク** — 何が観測されたら捨てるか。採用の代償
